# Source Browse Order Contract

## Authority

The backend owns browse order for all backend-paginated source-backed browse windows.
The renderer must not reorder backend windows.

## Scope

This contract applies to:

- **Literal hierarchy** source browsing, which is fixed and uses
  `name_browse_sort_key` for sibling directory/file rows
- **Contents source-file** ordering, which is fixed and uses
  `relative_path_browse_sort_key`

Contents primary-media remains metadata-first, and its `relative_path` fallback
is not converted yet. Library browser remains metadata-first and is not fully
converted. The renderer must not reorder backend windows.

## Ordering rule

Source hierarchy browsing uses **natural ordering** for numeric runs within
directory and file names. This means:

- `[1]` sorts before `[01]` which sorts before `[001]` which sorts before
  `[2]` which sorts before `[10]`
- `Track 1.wav` sorts before `Track 01.wav` which sorts before
  `Track 001.wav` which sorts before `Track 2.wav` which sorts before
  `Track 10.wav`
- Text comparisons are case-insensitive (primary) at the Unicode scalar level
- Digit runs are compared without fixed-width integer parsing:
  1. Fewer significant digits sorts first
  2. Significant digit bytes lexicographically ascending
  3. Same numeric value: shorter original digit-run length sorts first
  4. Same original length: original digit bytes lexicographically ascending
- Final tie-breaking uses original display name (case-sensitive) then stable
  row IDs

## Sort key persistence

Browse sort keys are computed and persisted at write/ingest time:

- `name_browse_sort_key` (per-component name sort key) in `source_directories` and `source_files`
- `relative_path_browse_sort_key` (path-level sort key) in `source_files`

The name sort key is generated by `compute_name_browse_sort_key(name)` and the
relative-path sort key by `compute_relative_path_browse_sort_key(relative_path)`,
both in `crates/library-store-sqlite/src/browse_sort_key.rs`.

### Sort key encoding (per-Unicode-scalar)

The sort key is stored as SQLite TEXT and ordered with BINARY collation.
The encoding is self-delimiting and deterministic:

1. Version prefix: `v1|`

2. For each component (name via `compute_name_browse_sort_key`, or each `/`-delimited
   path component via `compute_relative_path_browse_sort_key`), alternates between
   text runs and digit runs:
   - Text run: each Unicode scalar is folded to lowercase via `char::to_lowercase()`
     and encoded as `t` + the folded scalar. For scalars whose lowercase
     expansion produces multiple scalars, each is individually encoded with a `t`
     prefix.
   - Digit run: `d` + 5-digit zero-padded significant-length + `:` + significant
     digits + `:` + 5-digit zero-padded original-length + `:` + original digits

3. For relative-path sort keys, path components are separated by `/`.

The key is NOT guaranteed to be strictly ASCII for non-ASCII filenames
(e.g., `é` passes through after folding). For ASCII inputs the key is ASCII
printable.

### Numeric-run comparison properties

- Leading zeros are stripped to produce significant digits.
- An all-zero digit run is represented with significant `"0"`.
- Very large digit runs (hundreds of digits) compare correctly without
  parsing into a fixed-width integer type.
- Overflow cannot collapse a large numeric value to zero.

## SQL ordering in read models

### Literal hierarchy

```sql
ORDER BY sort_kind ASC,                 -- directories before files
         name_browse_sort_key ASC,       -- natural order (primary)
         display_name ASC,               -- case-sensitive tie-break
         COALESCE(source_directory_id, source_file_id) ASC  -- stable id
```

### Contents source-file

```sql
ORDER BY sf.relative_path_browse_sort_key ASC,  -- path-level natural order
         sf.relative_path ASC,                    -- case-sensitive tie-break
         sf.source_file_id ASC                    -- stable id
```

### Contents primary-media

Metadata-first ordering (availability, title, artist, album). The final
`relative_path` tie-break uses `lower(COALESCE(relative_path, ''))`.
Not yet converted to `relative_path_browse_sort_key`.

## Directory/file grouping

Directories always sort before files within the same parent (via `sort_kind`).
Within each group, natural order applies independently.

## Cursor contract

Contents source-file cursors (`CONTENTS_CURSOR_VERSION = 2`) carry:

- `relative_path_browse_sort_key`: the path-level browse sort key of the last row
- `relative_path`: the exact relative path of the last row
- `source_file_id`: the stable row ID

The cursor clause compares these three fields in order. Cursor version 1
cursors (which used `lower(relative_path)`) are invalidated. The cursor carries
the exact persisted `relative_path_browse_sort_key` selected from SQLite; read
models do not recompute it from `relative_path`.

## Non-goals

- Locale-sensitive human collation (e.g., ICU locale-aware ordering)
- Metadata title/artist/album natural ordering (library browser uses its own ordering)
- Track identity ordering
- Playlist, crate, sleeve, prep, waveform, stems, or artwork ordering
- Renderer-side reordering of backend-paginated windows

## Remaining browse-order sites

The following surfaces have not yet been migrated to natural browse sort keys:

| Surface | File | Current ordering | Backend paginated | Requires cursor change |
|---|---|---|---|---|
| **Contents primary-media** | `contents.rs` `PRIMARY_MEDIA_CONTENTS_ORDER_SQL` | `lower(title/artist/album/relative_path)` | Yes | Yes |
| **Library browser default** | `library_browser.rs` `AGGREGATE_DEFAULT_ORDER` | `lower(title/artist/album/relative_path)` | Offset-based (no cursor) | No |
| **Library browser scoped** | `library_browser.rs` `read_scoped_window_rows` | `lower(title/artist/album/relative_path)` | Offset-based (no cursor) | No |
| **Library browser prep-policy** | `library_browser.rs` `read_prep_policy_window_rows` | `lower(title/artist/album/relative_path)` | Offset-based (no cursor) | No |
| **Library browser search** | `library_browser.rs` search order clauses | `lower(title/artist/album/relative_path)` | Offset-based (no cursor) | No |
| **Navigation** | `navigation.rs` (projections) | `sibling_position` | No | N/A |
| **Playlists** | `projections.rs` | `lower(display_name)` | No | N/A |

### Rationale for deferral

Primary-media and library-browser surfaces are metadata-ordered (title/artist/album).
The `lower(relative_path)` is used only as a final tie-break for rows with identical
metadata values. The `[10]` before `[2]` class of bug in these tie-breaks is unlikely
to be visible to users. Converting these requires either joining `source_files` to
obtain `relative_path_browse_sort_key` in the projected row set, or computing
a separate column on the projected table. Both paths carry migration complexity
disproportionate to the user-facing impact.

Literal hierarchy and contents source-file ordering are now fixed.

## Schema

```sql
source_directories.name_browse_sort_key TEXT NOT NULL
source_files.name_browse_sort_key TEXT NOT NULL
source_files.relative_path_browse_sort_key TEXT NOT NULL

CREATE INDEX source_files_source_browse_order
    ON source_files (
        source_id,
        relative_path_browse_sort_key,
        relative_path,
        source_file_id
    );
```

The directory name key and both file keys are populated by the authority write
paths (`source_directories.rs`, `source_files.rs`, and `discovery.rs`) with no
`DEFAULT ''` fallback.
The source-file browse-order index matches the whole-source contents ordering;
more selective path-scoped queries may continue to use the binary relative-path
index for scope filtering.
