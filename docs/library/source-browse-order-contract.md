# Source Browse Order Contract

## Authority

The backend owns browse order for paginated source hierarchy literal browsing.
The renderer must not reorder backend windows.

## Scope

**This contract currently applies to literal hierarchy source browsing only.**

Contents and library browser ordering remain separate read-model contracts with
lexicographic `lower()` ordering. Those surfaces are not yet migrated to natural
browse sort keys.

## Ordering rule

Source hierarchy browsing uses **natural ordering** for numeric runs within
directory and file names. This means:

- `[1]` sorts before `[01]` which sorts before `[001]` which sorts before
  `[2]` which sorts before `[10]`
- `Track 1.wav` sorts before `Track 01.wav` which sorts before
  `Track 001.wav` which sorts before `Track 2.wav` which sorts before
  `Track 10.wav`
- Text comparisons are case-insensitive (primary)
- Digit runs are compared without fixed-width integer parsing:
  1. Fewer significant digits sorts first
  2. Significant digit bytes lexicographically ascending
  3. Same numeric value: shorter original digit-run length sorts first
  4. Same original length: original digit bytes lexicographically ascending
- Final tie-breaking uses original display name (case-sensitive) then stable
  row IDs

## Sort key persistence

Browse sort keys are computed and persisted at write/ingest time in the
`name_browse_sort_key` column of `source_directories` and `source_files`.

The sort key is generated by `compute_name_browse_sort_key(name)` in
`crates/library-store-sqlite/src/browse_sort_key.rs`.

### Sort key encoding (ASCII text)

The sort key is **ASCII printable text**, stored as SQLite TEXT and ordered
with BINARY collation. The encoding is self-delimiting and deterministic:

1. Version prefix: `v1|`
2. For each segment of the name (alternating text and digit runs), one of:
   - Text run: `t` + 5-digit zero-padded decimal length + `:` + lowercase-folded text
   - Digit run: `d` + 5-digit zero-padded significant-length + `:` + significant
     digits + `:` + 5-digit zero-padded original-length + `:` + original digits

### Numeric-run comparison properties

- Leading zeros are stripped to produce significant digits.
- An all-zero digit run is represented with significant `"0"`.
- Very large digit runs (hundreds of digits) compare correctly without
  parsing into a fixed-width integer type.
- Overflow cannot collapse a large numeric value to zero.

## SQL ordering in read models

The literal hierarchy read model orders child rows by:

```sql
ORDER BY sort_kind ASC,                 -- directories before files
         name_browse_sort_key ASC,       -- natural order (primary)
         display_name ASC,               -- case-sensitive tie-break
         COALESCE(source_directory_id, source_file_id) ASC  -- stable id
```

## Directory/file grouping

Directories always sort before files within the same parent (via `sort_kind`).
Within each group, natural order applies independently.

## Non-goals

- Locale-sensitive human collation (e.g., ICU locale-aware ordering)
- Metadata title/artist/album ordering (library browser uses its own ordering)
- Track identity ordering
- Playlist, crate, sleeve, prep, waveform, stems, or artwork ordering
- Renderer-side reordering of backend-paginated windows

### Contents surface detail

`contents.rs` source-file rows use cursor positions based on
`lower(relative_path)`. The ORDER BY clause uses
`SOURCE_FILE_CONTENTS_ORDER_SQL` which sorts by `lower(COALESCE(relative_path, ''))`.
This means `[10].wav` still sorts before `[2].wav` in the contents view.

Fixing contents ordering requires:
1. Changing `SOURCE_FILE_CONTENTS_ORDER_SQL` to use `name_browse_sort_key`
2. Updating `ContentsCursorPosition::SourceFile` to carry sort-key positions
   instead of lowercase relative_path keys
3. Updating cursor clause generation to compare browse sort keys
4. Testing pagination stability after the change

### Library browser surface detail

Library browser ordering is metadata-based (title, artist, album) with
relative_path as tie-break, not source-browsing order. The `[10]` < `[2]`
bug is not applicable because relative_path is used only as a final
tie-break for rows with identical metadata.
