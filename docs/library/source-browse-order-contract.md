# Source Browse Order Contract

## Authority

The backend owns browse order for all paginated source/folder/file reads.
The renderer must not reorder backend windows.

## Ordering rule

Source hierarchy browsing uses **natural ordering** for numeric runs within
directory and file names. This means:

- `[1]` sorts before `[2]` which sorts before `[10]`
- `Track 1.wav` sorts before `Track 2.wav` which sorts before `Track 10.wav`
- Text comparisons are case-insensitive (primary)
- Digit runs compare by numeric value, not lexicographic length
- Leading zeros preserve deterministic tie-breaking: `01` < `1` < `001`
  (shorter digit string at same numeric value sorts first)
- Final tie-breaking uses original display name (case-sensitive) then stable
  row IDs

## Sort key persistence

Browse sort keys are computed and persisted at write/ingest time in the
`name_browse_sort_key` column of `source_directories` and `source_files`.

The sort key is generated by `compute_name_browse_sort_key(name)` in
`crates/library-store-sqlite/src/browse_sort_key.rs`.

The key encoding:
1. Version byte `\x01`
2. For each segment of the name (alternating text and digit runs):
   - Text segment: `\x02` + lowercase text
   - Digit segment: `\x03` + 19-digit zero-padded numeric value + original
     digit string
3. End marker `\x04`

This encoding ensures correct lexicographic ordering in SQLite's BINARY
collation.

## SQL ordering in read models

The literal hierarchy read model orders child rows by:

```sql
ORDER BY sort_kind ASC,           -- directories before files
         name_browse_sort_key ASC, -- natural order (primary)
         name ASC,                 -- case-sensitive tie-break
         COALESCE(source_directory_id, source_file_id) ASC  -- stable id
```

## Directory/file grouping

Directories always sort before files within the same parent (via `sort_kind`).
Within each group, natural order applies independently.

## Non-goals

- Locale-sensitive human collation (e.g., ICU locale-aware ordering)
- Metadata title/artist/album ordering (library browser uses its own ordering)
- Track identity ordering
- Playlist, crate, sleeve, prep, waveform, stems, or artwork ordering
- Renderer-side reordering of backend-paginated windows

## Remaining browse-order sites

The following read models still use lexicographic ordering and may need future
updates for natural ordering:

| Read model | Current ordering | Risk |
|---|---|---|
| `contents.rs` SOURCE_FILE_CONTENTS_ORDER_SQL | `lower(relative_path)` | Medium: file listing in contents view |
| `library_browser.rs` AGGREGATE_DEFAULT_ORDER | `lower(title)`, `lower(artist)`, `lower(album)` | Low: metadata ordering, not source browse |
| `navigation.rs` | `sibling_position` | None: explicit user-defined ordering |
| `navigation_reads.rs` | path-based resolution, no browse ordering | None |

These sites use metadata (title/artist/album) or explicit position rather than
raw filesystem names, so they are not affected by the same numeric-misordering
bug.
